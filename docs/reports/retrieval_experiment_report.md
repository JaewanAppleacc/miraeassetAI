# Retrieval 성능 개선 실험 라운드 — 결과 보고

**평가 조건**: Stage 1 실제 후보 문서 기반 평가이며, 현재 구축된 후보 문서 캐시(top-70 · 756건) 범위 내에서 측정.
gold 문서만으로 Stage 2를 구성하지 않았고, gold evidence는 채점 단계에서만 사용했다. LLM 호출 0회. production 코드 무수정.

> **기준선 구분** — 과거 보고된 `E-R@20 = 0.9429 / HIT 131`은 gold 문서 50건 본문만 Stage 2에 넣던
> **낙관적(historical) 조건**의 수치다. 이번 라운드의 진짜 기준선은 실제 후보 문서 조건의
> **`E-R@20 = 0.7429 / HIT 104 / P1 3 / P2 22 / P4 11`** 이다. 둘을 섞어 읽으면 안 된다.

## A. 현재 baseline (Phase 2 재현 확인)

```
E-R@20: 0.7429     HIT: 104 / 140
P1: 3   P2: 22   P4: 11
Stage2 문서 37.7 / 질문 · Stage2 청크 12,706 / 질문
```
기대치와 **완전 일치** — 이후 실험을 진행할 조건 충족.

## B. 청킹 (Phase 3)

가장 좋은 3개:

1. **A0 production line_window** — @20 0.7429 · HIT 104 (1순위 지표 최고, 변경 없음)
2. **A1 paragraph** — @20 0.7357(−0.0072) · **@1 0.2071**(+0.0571) · **P4 9**(−2) · 청크 10,381
3. **A2 heading+paragraph** — @20 0.7357 · @1 0.2000 · P4 10 · 중복률 최저(0.303)

기각: **A3/A4 표 행 단위** — 청크가 12.7k → 53.9k로 4배, HIT 104 → 44/49, P2 22 → 61/59, 중복률 0.56.
표를 행으로 쪼개면 실제 경쟁 환경에서 신호가 희석된다. **A5-small(6/4)** 도 HIT 85로 악화.

## C. Retrieval 모델 (Phase 4)

| | @5 | @20 | HIT | P4 | 전처리 |
|---|---:|---:|---:|---:|---:|
| BM25 (현행) | 0.5143 | **0.7429** | **104** | 11 | 54ms |
| BM25 + Kiwi 형태소 (A0) | 0.3500 | 0.6857 | 96 | **18** | 24,663ms |
| BM25 + Kiwi 형태소 (A1) | 0.3143 | 0.5857 | 82 | 19 | (캐시 재사용) |

**Kiwi REJECT.** @20 −0.0572 · HIT −8 · **P4 악화(11 → 18)** · Q14 최선 순위 2 → 236.
원인: production 토크나이저가 이미 한글 음절 bigram이라 조사 변화에 강건한데, Kiwi로 명사만 남기면
숫자·표 구조 토큰이 사라져 매칭이 오히려 약해진다. (기존 벤치마크에서 Kiwi가 이겼던 비교 대상은
tantivy whitespace 토크나이저라 전제가 다르다.)

**Dense 전면 검색은 실행 불가**: bge-m3 CPU 실측 3.2 chunks/s, 문항당 청크 12,706개 →
variant 하나에 수 시간. faiss 없음, GPU 없음. Phase 6 reranker로만 측정했다.

## D. Hybrid (Phase 5)

**실행하지 않음.** RRF는 dense 순위를 필요로 하는데, dense 점수 산출 자체가 문항당 75초(아래 E)라
hybrid를 붙여도 실사용 불가가 확정된다. 의사결정 가치가 없어 중단(종료 조건 3·4).

## E. Reranker (Phase 6)

| | @1 | @5 | @20 | HIT | P2 | P4 | rerank latency |
|---|---:|---:|---:|---:|---:|---:|---:|
| BM25 (baseline) | 0.1500 | 0.5143 | 0.7429 | 104 | 22 | 11 | — |
| + bge-m3 rerank top-50 | 0.1929 | 0.3857 | 0.7286 | 102 | 23 | 12 | **75,270ms** (최대 192,022ms) |

**REJECT.** @1은 올랐지만 @5가 0.5143 → 0.3857로 붕괴, @20·HIT 모두 하락.
문항당 75초는 현재 전체 검색(216ms) 대비 세 자릿수 배다.
top-100 · RRF · KURE-v1 · PIXIE-Rune은 **실행하지 않았다** — 같은 latency 벽에 갇혀 결과와 무관하게
production REJECT가 확정되므로.

## I. Production 적용 여부

```
DO NOT RECOMMEND
```

이유:
1. 어떤 조합도 1순위 지표(E-R@20)와 2순위(HIT)에서 baseline을 넘지 못했다.
2. 병목인 P2 22 · P4 11을 줄인 조합이 하나도 없다. 오히려 Kiwi(P4 18)·표 행 청킹(P4 32)은 악화.
3. dense 계열은 이 환경(CPU·faiss 없음)에서 latency가 실사용 한계를 세 자릿수 배 초과.

### 다만 별도 기록 — Weak candidate

**A1 paragraph 청킹**: @20 −0.0072(사실상 동률)이면서 **@1 +0.0571 · P4 −2 · 청크 −18% · latency −19%**.
답변 문맥으로 상위 소수를 넘기는 현재 Agent 구조에서는 @1/@3이 실제 답변 품질에 더 가깝다.
채택하려면 Agent 단계 지표(gold 근거의 LLM 발췌 포함률)로 한 번 더 재는 것이 맞고, 이번 라운드
채택 기준(E-R@20 개선)으로는 미달이다.
